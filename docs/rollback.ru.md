# Откат

[English](rollback.md) | Русский

Миграции базы не откатываются: база, которую мигрировала новая сборка, не работает
под старым кодом. Поэтому откат всегда означает СТАРЫЙ код и СТАРУЮ базу (бэкап или
копия, сохранённая переносом), и порядок шагов важен.

## 1. После переноса со старого форка (обычный путь)

Если установка пришла со старого форка (`040410ac`) через
[migrate-from-fork](migrate-from-fork.ru.md), возвращайтесь его собственной командой;
это первый выбор, и своего бэкапа он не требует:

```bash
cd /opt/iceslab-new
scripts/ops/migrate-from-fork.sh --rollback --panel-dir /opt/iceslab
```

Она возвращает базу, сохранённую как `<db>_pre_fork`, переключает старый код, помечает
старые образы текущими и запускает старую панель. Что менялось в панели после переноса,
теряется. Перенесённая база остаётся как `<db>_migrated_<время>`.

## 2. После обычного обновления этого форка

Для случая, когда вы обновили этот форк через `scripts/ops/deploy.sh` и хотите прежнюю
ссылку. Нужен бэкап, снятый ДО обновления (`scripts/ops/iceslab-backup.sh`); бэкап после
него уже содержит новую схему.

```bash
cd /opt/iceslab
# 0. (один раз, до обновления) бэкап старого состояния
scripts/ops/iceslab-backup.sh --out ./backups
# ... обновление, неприятности ...
# 1. старый код и его образы
git checkout <старая ссылка>
ICESLAB_REF=<старая ссылка> scripts/ops/deploy.sh
# 2. старая база, панель стартует из старых образов
scripts/ops/iceslab-restore.sh ./backups/iceslab-backup-<время>.tar.gz
```

Почему именно так:

- Миграции новой сборки остаются в базе. `deploy.sh` старой ссылки пересобирает старые
  образы, затем restore кладёт под них старую базу. Если сначала восстановить, а потом
  переключить код, на старой базе окажется новая сборка, и её шаг `migrate` накатит
  миграции снова.
- `iceslab-restore.sh` поднимает `backend` и `frontend` через `docker compose up -d` из
  текущего компоуза и образов (включая шаг `migrate`), то есть работает сборка
  текущей копии, а не те контейнеры, что остались.
- Restore останавливает панель, пересоздаёт базу, загружает дамп и снимок Redis и не
  перезаписывает `.env.production` (копия из архива кладётся отдельно, путь печатается).

Теперь бэкап записывает в `manifest.json` коммит (`gitSha`, если установка — git-копия) и
миграции (`migrations`: число и имя последней). Restore печатает их и ПРЕДУПРЕЖДАЕТ, не
отказывая, если в базе архива есть миграции, которых нет в текущем коде: тогда сначала шаг 1
(коммит назван в сообщении). Архив, снятый до этой версии, полей не имеет и восстанавливается
как раньше.

### Restore из `v0.3.1`

`iceslab-restore.sh` версии `v0.3.1` делает `docker compose start backend frontend`:
стартуют оставшиеся контейнеры, какой бы сборки они ни были. Поэтому перед restore этим
скриптом контейнеры новой сборки должны быть заменены `deploy.sh` старой ссылки (шаг 1
выше); без контейнеров он падает на отсутствующей зависимости `migrate`. Если
восстанавливаете скриптом `v0.3.1`, сначала выполните `ICESLAB_REF=v0.3.1
scripts/ops/deploy.sh`, как выше, и проверьте по `docker ps`, что образы этой сборки.

## Что откат не возвращает

Изменения, сделанные в панели после бэкапа (пользователи, хосты, трафик), и то, что нодам
сообщили с тех пор. Ноды работают на последней конфигурации и принимают восстановленную при
следующей рассылке.
